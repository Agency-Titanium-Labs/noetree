<objective>
Execute the Stripe cutover: create the Premium prices, migrate every existing active Pro subscriber onto the new Premium monthly price with no billing disruption, and archive the old price — first entirely in Stripe test mode, then in live mode.

Purpose: PLAN-09's success criterion is about the state of real billing objects, not about code. Plans 12-02 and 12-04 built and unit-tested the tooling; nothing has touched Stripe yet. This plan is the operator-gated execution, and it is deliberately the last plan in the phase.

Output: Premium prices existing in both Stripe modes, all active subscribers migrated, the old price archived, and the evidence recorded in the summary.

Every task here is a blocking checkpoint. Claude runs no Stripe command in this plan — it does not hold a Stripe secret key, and a live-billing mutation is never an autonomous action.
</objective>

Webhook path affected by the migration burst (UNCHANGED by this phase — no action required, only observation):
Stripe customer.subscription.updated -> app/api/webhooks/stripe/route.ts
-> convex/stripeWebhooks.ts processWebhookEvent
-> internal.subscriptions.upsertSubscription (idempotent via the processedStripeEvents table)
The Convex subscriptions row stores status/currentPeriodEnd/cancelAtPeriodEnd only — it has no priceId
field, so a successful migration produces no visible change in Convex data. Do not treat that as a failure.

<threat_model>

## Trust Boundaries

| Boundary                               | Description                                                           |
| -------------------------------------- | --------------------------------------------------------------------- |
| operator shell → Stripe LIVE API       | Irreversible mutations against real paying customers' subscriptions   |
| test mode → live mode                  | Two separate credential/price-ID universes that must never be mixed   |
| migration burst → app webhook endpoint | A spike of `customer.subscription.updated` events re-entering the app |

| Threat ID  | Category               | Component                                                               | Disposition | Mitigation Plan                                                                                                                                                                                                                                                                                                        |
| ---------- | ---------------------- | ----------------------------------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| T-12-06-02 | Tampering              | unintended mid-cycle charge to a real customer                          | mitigate    | The dry run in step 4 must match the baseline count before any mutation, and the post-run spot check (step 6) explicitly verifies no invoice was created and no next-invoice date moved — the direct observable form of D-01.                                                                                          |
