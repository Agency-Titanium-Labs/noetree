# Stack Research

**Domain:** Peer-to-peer digital goods marketplace (notes) with Stripe Connect payouts, seller-set pricing, and a 15% platform commission — added onto an existing Next.js 15 + Convex + Clerk + Stripe (non-Connect) application
**Researched:** 2026-07-12
**Confidence:** HIGH (Stripe Connect core mechanics verified via Context7 `stripe-node` source + official Stripe docs; MEDIUM/LOW flags called out below for the newer "Accounts v2" path)

**Scope:** Additions/changes only for the v1.1 marketplace milestone. Next.js 15, Convex, Clerk, Shadcn UI, Tailwind, and the existing non-Connect Stripe subscription/top-up integration (`app/api/webhooks/stripe/route.ts` → `convex/stripeWebhooks.ts`) are NOT re-evaluated — see the archived v1.0 research for that.

## Alternatives Considered

| Recommended                                                                                            | Alternative                                                                                                      | When to Use Alternative                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Express** connected accounts                                                                         | **Standard** connected accounts                                                                                  | If sellers are expected to already run an established Stripe-powered business (e.g., B2B resellers) and the platform wants zero liability for negative balances/disputes. Standard costs the platform nothing per-account, but gives sellers a full Stripe Dashboard and a "connect your existing Stripe account" flow — a poor fit here, since any Free/Pro user can casually become a seller ("Vente ouverte à tous") and most will have no existing Stripe account.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Express** connected accounts                                                                         | **Custom** connected accounts                                                                                    | Only if the product needs a 100% white-labeled experience with zero Stripe branding anywhere, and is willing to build and maintain all KYC/identity-collection UI plus the associated compliance obligations. Far too much surface area for this milestone — explicitly avoid.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Destination charges (one Checkout Session with `application_fee_amount` + `transfer_data.destination`) | Separate charges and transfers (charge the platform account, then a distinct `stripe.transfers.create` call)     | Only needed once a single order can span **multiple sellers** in one checkout (e.g., a future "cart" spanning notes from 3 different sellers). A single Checkout Session/PaymentIntent can only carry one `transfer_data.destination`, so destination charges cannot split across multiple connected accounts. Current scope is always one note (or note+subtree) = one seller = one Checkout Session, so destination charges are simpler and sufficient — do not build separate-charges-and-transfers infrastructure preemptively.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Accounts **v1** (`type: 'express'`)                                                                    | Accounts **v2** (configuration-based: `merchant` / `customer` / `recipient` configs on a unified Account object) | Stripe GA'd Accounts v2 in Q2 2026 and recommends it for brand-new integrations going forward, unifying the connected-account and customer identity model. However: (a) Stripe explicitly states existing v1 integrations do not need to migrate, (b) publicly available guidance on wiring a v2-configured account through a plain Checkout Session with `application_fee_amount`/`transfer_data` was not confirmed as mature during this research, and (c) the existing non-Connect Stripe usage in this app (Customers, Subscriptions) is entirely v1-style — introducing a v2 Connect flow into a v1-Customer codebase adds conceptual overhead for no MVP benefit. **Recommendation: build v1.1 on v1 Express; re-evaluate v2 in a later milestone** once its Checkout/Connect documentation matures. Flagged LOW-MEDIUM confidence — this is the one area of this research that changed meaningfully in recent months and should be spot-checked against current Stripe docs again before implementation begins. |
| Convex native `.searchIndex()`                                                                         | Algolia / Typesense / Meilisearch                                                                                | Only if marketplace search later needs typo-tolerance, tuned relevance ranking, faceted search at large scale, or cross-field ranking beyond what a Convex search index provides. At MVP scale (browsing a catalog of user-listed notes), Convex's built-in search index (search on title/description + `filterFields` for tags/status) is sufficient and avoids introducing a second data store to keep in sync with Convex.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

## What NOT to Use

| Avoid                                                                                 | Why                                                                                                                                                                                                                                                                                 | Use Instead                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Custom connected accounts                                                             | Requires building bespoke KYC/identity-collection forms and taking on far more compliance responsibility (identity document collection/validation, ToS acceptance flows, etc.)                                                                                                      | Express accounts (Stripe-hosted onboarding via Account Links)                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Manual `stripe.transfers.create` calls for a single-seller checkout                   | Adds a second API call, a window where the charge succeeds but the transfer could fail, and manual reconciliation — unnecessary when destination charges do both atomically                                                                                                         | `payment_intent_data.application_fee_amount` + `payment_intent_data.transfer_data.destination` on the same Checkout Session                                                                                                                                                                                                                                                                                                                                                                                 |
| Reusing the **existing** Stripe webhook endpoint/secret unmodified for Connect events | Connected-account events (`account.updated`, `capability.updated`, etc.) are a **separate event stream** with their own signing secret, even when pointed at the same URL — verifying them with the existing (platform) `STRIPE_WEBHOOK_SECRET` will silently fail signature checks | Add a **second Stripe webhook endpoint** (Dashboard → Webhooks → enable "Listen to events on Connected accounts", or register a second endpoint), store its distinct signing secret in a new env var (e.g. `STRIPE_CONNECT_WEBHOOK_SECRET`), and use the event's top-level `account` field to identify which connected account it belongs to. Extend the existing `processedStripeEvents` idempotency table to also record Connect-stream event IDs (they are a separate ID sequence from platform events). |
| A brand-new Stripe account / separate Stripe "platform" for the marketplace           | Unnecessary — Connect is additive on the **same** Stripe account already used for subscriptions/top-ups                                                                                                                                                                             | Enable Connect on the existing Stripe account (test mode first); connected accounts (`acct_...`) live alongside existing Customers/Subscriptions without conflict                                                                                                                                                                                                                                                                                                                                           |
| External search service (Algolia, etc.) for MVP                                       | Overkill for a first marketplace listings catalog; introduces a second system to keep in sync with Convex                                                                                                                                                                           | Convex `.searchIndex()` (native, already in the stack)                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `@stripe/react-stripe-js` / embedded Stripe Elements for checkout                     | Marketplace checkout uses redirect-based Checkout Sessions (same pattern as existing subscription/top-up flows) — no card Elements needed                                                                                                                                           | `@stripe/stripe-js` `loadStripe()` + `redirectToCheckout`/hosted Checkout URL, exactly as already used                                                                                                                                                                                                                                                                                                                                                                                                      |

## Stack Patterns by Variant

**If checkout is always exactly one seller per order (current scope — single note or note+subtree purchase):**

- Use one Checkout Session per purchase, `mode: 'payment'`, with `payment_intent_data.application_fee_amount` (15% of the seller-set price, computed and rounded server-side in Convex/Next.js — never trust a client-supplied fee) and `payment_intent_data.transfer_data.destination` set to the seller's connected account ID. Attach `metadata` (noteId, sellerId, buyerId, listing mode: copy vs read-only) so the webhook handler can act without a second lookup.
- Because this is the simplest charge type Stripe recommends for exactly this transaction shape, and requires no post-payment reconciliation step.

**If a future milestone adds a multi-seller cart:**

- Switch to "separate charges and transfers": charge the buyer once on the platform account, then issue one `stripe.transfers.create` per seller line item, each with its own computed commission withheld.
- Because a single Checkout Session/PaymentIntent can only have one `transfer_data.destination` — destination charges cannot split across multiple connected accounts in one charge.

**For seller onboarding UX:**

- Use Account Links (`stripe.accountLinks.create({ type: 'account_onboarding', account, refresh_url, return_url })`) redirecting to Stripe-hosted pages, then redirect back into the app; poll/read the account's `charges_enabled`/`details_submitted` (or check via a webhook on `account.updated`) to know when a seller can start listing notes for sale.
- Because it requires no embedded-components integration, ships fastest, and is fully Stripe-hosted/maintained (Stripe updates the KYC forms as regulations change, with zero app code changes needed).

**For gating "sell" actions before onboarding completes:**

- Store a `sellerOnboardingStatus` field (e.g. `"not_started" | "pending" | "active"`) on the user record in Convex, updated from the Connect webhook stream (`account.updated` → check `charges_enabled` + `payouts_enabled`). Block listing creation/checkout button until `"active"`.
- Because relying on a client-side redirect return alone is not sufficient — a seller can abandon or fail Stripe's hosted onboarding after being redirected back, and only the webhook is authoritative for verification/capability state, matching this project's existing convention of Convex being the store of truth fed by Stripe webhooks.
